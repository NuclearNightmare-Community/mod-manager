# Mod Manager

A Nuclear Nightmare mod that adds **MANAGE MODS** to the title-screen menu, between OPTIONS and QUIT. It opens a **MOD MANAGER** window (on Nucleus's window card) that lists every installed mod, one row each: `toggle | name | version | scope | status icons | gear`. A player can turn mods on and off for the next start, see what needs attention, change a mod's settings and quit the game to apply the changes. Built on **Nucleus** (core): its menu entry, windows, lists, rows, images, checkbox, choice and slider controls are core's (`core.ui`), and settings go through core's settings service (`core.settings`). Spec: `_bmad-output/specs/spec-mod-manager-v1/` in the workspace (stories 3 and 6).

- Scope `client`: it reads and writes the local game folder only, sends nothing over the network and reads nothing from other players.
- Version 0.4.0, built for game V8.2.3 (build 26601774) and UE4SS `v3.0.1-1181-g83330635`. Needs Nucleus `>=0.21.0` (the scope icons; `core.restart` since 0.20.0, for RESTART NOW).
- Id `nuclearnightmare-community.mod-manager`; folder, `mods.txt` line and log tag `ModManager` (UE4SS removes spaces from `mods.txt` lines, so the folder can't be `Mod Manager`); shown as "Mod Manager" through `displayName`.
- License: MIT (`LICENSE`); changes: `CHANGELOG.md`; `build.ps1` stages the release package for the workspace's `tools/release/release.ps1`.

## Install

Nucleus 0.21.0 or newer must be installed in the dev copy first (its own `deploy.ps1`). Then, from this repo (from a worktree, pass the main checkout's instance path):

```powershell
./deploy.ps1 -Instance C:\...\nuclear-nightmare\game-instances\v8.2.3-build26601774
./deploy.ps1 -Instance C:\...\nuclear-nightmare\game-instances\v8.2.3-build26601774 -Remove
```

`deploy.ps1` refuses, with one line and exit code 1, when Nucleus isn't installed in the copy, is disabled in `mods.txt`, or its installed `mod.json` version doesn't satisfy `dependsOn` (`>=0.21.0`: a minimum, and not below the installed core's `compat.floor`). Core's `dependsOn` entry is the one whose id names Nucleus: `nuclearnightmare-community.nucleus`, compared through the id normalizer (any case, or the `github.com/` long form). Otherwise it copies `mod.json` and `Scripts/` to `Mods/ModManager/` (replacing the folder, so a dev copy's `state.json` goes too) and puts `ModManager : 1` in `mods.txt` right below Nucleus's line and above `Keybinds : 1`. It never bundles core's files and ships no `state.json`. `-Remove` takes all of it out again; `mods.txt` keeps its exact bytes otherwise.

Launch only with the workspace's `tools/launch.ps1 -Instance <copy>`.

## What it shows

- **Rows:** one per folder `ue4ss/Mods/<F>` whose name is 1-64 of `A-Z a-z 0-9 _ -`, except UE4SS's own mods (`BPML_GenericFunctions`, `BPModLoaderMod`, `CheatManagerEnablerMod`, `ConsoleCommandsMod`, `ConsoleEnablerMod`, `Keybinds`, `LineTraceMod`, `SplitScreenMod`) and `shared`. `<F>_P.pak[.disabled]` (`_P` in any case, or no `_P` at all) in `Content/Paks`, and `<F>.pak[.disabled]` in `Content/Paks/LogicMods` or one of its subfolders (BPModLoaderMod loads those too; a subfolder whose name isn't a mod name is skipped with one WARN), belong to folder `<F>`'s row; a pak with no folder is its own row (named after the file without `_P`, version `UNMANAGED`), and a pak named like a UE4SS built-in or `shared` is never a row. The game's own paks (`NuclearNightmare-Windows.*`, `pakchunk*`) and `.utoc`/`.ucas` files are never rows.
- **Order:** Nucleus, the Mod Manager, then the rest by shown name, ignoring case. At most 200 rows (one `WARN` when there are more).
- **On/off as read:** on when the folder has `enabled.txt` or a `mods.txt` line whose value starts with `1` (UE4SS's own reading: a line with `;` or of 4 characters or fewer is skipped, spaces are removed, the name before the first `:` matches exactly); a pak-only row is on when one of its paks is `.pak`.
- **Toggle:** core's checkbox, tooltip `ON`/`OFF`. Nucleus and the Mod Manager show a lock (`ALWAYS ON`) instead. A pak-only row, or a folder row with a joined pak, shows its state in a disabled checkbox (`BLUEPRINT MODS CAN'T BE SWITCHED FROM THE GAME YET`; see "What it writes").
- **Name:** `displayName`, else `name`, else the folder name. A `displayName` that isn't 1-64 characters, with no control character and no leading or trailing space, is ignored (one `WARN` per folder per session). Cut with `…` at its column's edge.
- **Version:** `version`, `-` when missing or unreadable, `UNMANAGED` for a pak-only row. Values are capped at 64 characters (a bound on untrusted input, not a width).
- **Where it runs** (story 12): one icon per row from the mod's top-level `mod.json` `scope` (distribution story 14's vocabulary, Nucleus's `scope-*` icons), with its words as the tooltip and again as Configure's `RUNS ON:` line, which keyboard and gamepad players reach through the gear (an icon takes no focus and a tooltip shows on hover only):

  | `scope` | Icon | Words |
  |---|---|---|
  | `host` | a house | `HOST ONLY - ONLY THE HOST NEEDS IT; PLAYERS WHO JOIN DON'T` |
  | `client` | a person | `JUST YOU - WORKS ON ITS OWN, WHETHER YOU HOST OR JOIN` |
  | `host-plus` | a house with a small person | `HOST, PLAYERS OPTIONAL - THE HOST NEEDS IT; PLAYERS WHO HAVE IT GET MORE` |
  | `both` | a house and a person with a plus | `HOST AND PLAYERS - THE HOST AND EVERY PLAYER NEED IT` |
  | anything else | a question mark in a ring | `UNKNOWN - THIS MOD DOESN'T SAY WHERE IT RUNS` |

  The match is exact and case-sensitive; a missing scope, the retired `all`, `Host`, `""`, a non-string, a pak-only row and a folder without a readable `mod.json` are unknown, with no `WARN`, and the raw value is never shown or logged. A setting's own `scope` (in `settings`) never counts. The icon only informs: nothing is turned off or hidden because of it.
- **Status icons** (three fixed slots, filled left to right; pak-only rows never get one), each with a tooltip:
  - **Other game build** (warning): the mod's `game.build` differs from the running build when both are known, else its `game.version` from the running version; unknown on either side shows nothing. The running version is the last `V<digit>...` token of the title-screen footer (`NUCLEAR NIGHTMARE EA V8.2.3`), the running build Steam's `appmanifest_2909110.acf` two folders above the game's install folder (read only; a dev copy has none: build unknown). Tooltip `MADE FOR GAME <ver> (BUILD <b>). THIS GAME: <ver> (BUILD <b or ->).`
  - **Dependency** (warning): for each `dependsOn` entry (id through core's normalizer; a bare `nucleus` is read as core's legacy id here; an entry that doesn't normalize is skipped): `NEEDS <id> (NOT INSTALLED)`, `NEEDS <name> (TURNED OFF)`, or `NEEDS <name> <need> (INSTALLED: <ver>)` when the installed version doesn't meet the need (or is unknown). One icon, one line per problem. Shown for every managed row, on or off; it never turns anything off.
  - **Restart** (restart): the row is pending: its on/off in the files differs from what UE4SS started this session (the first scan after `onReady`), or one of its settings waits for a restart. `TURNS ON AFTER A RESTART` / `TURNS OFF AFTER A RESTART` / `A SETTING APPLIES AFTER A RESTART`.
- **Gear:** lit when `mod.json` declares a non-empty `settings` object, dimmed otherwise; either way it opens **Configure** (below).
- **Banner and QUIT GAME:** while any row is pending, `CHANGES APPLY AFTER A RESTART.` and a `QUIT GAME` button show in the window's bottom-right corner. QUIT GAME logs `QUIT pending=<n>` and calls `KismetSystemLibrary:QuitGame` (a fresh PlayerController, nothing kept); the player starts the game again.
- **RESTART NOW** (story 8): right above QUIT GAME, shown with it only when `core.restart.mode()` (Nucleus 0.20.0) gives a mode: `steam` (Steam's `appmanifest_2909110.acf` two folders above the game folder: Steam starts the game again, with the player's launch options) or `direct` (a dev copy with `steam_appid.txt` beside the exe: the same exe and command line, `-userdir` included). The mode is asked once per session at the first open (`RESTARTMODE <mode>` or `RESTARTMODE none (<why>)`). A click calls `core.restart.start()`, which starts Nucleus's relaunch helper (`Mods/Nucleus/bin/NucleusRestart.exe`; it waits for this game to exit, then starts it again); on `true`, or `nil, "already started"` (a helper is already waiting), it logs `RESTART mode=<m> pending=<n>` and runs the same `QuitGame` as QUIT GAME. Any other answer (`helper missing`, `start failed: <code>`, ...) leaves the game running, shows `CAN'T RESTART: USE QUIT GAME AND START THE GAME AGAIN.` on the message line and logs one `WARN RESTART NOW could not restart the game (<why>); the game keeps running` per reason. With neither a manifest nor `steam_appid.txt`, or a Nucleus without `core.restart`, only QUIT GAME shows. Pending pak renames are not applied by the restart (still open: story 6's decision).
- **Nucleus build alert:** when Nucleus's own row shows the build icon, the first open shows one alert window (`NUCLEUS <v> WAS MADE FOR GAME <x>. THIS GAME IS <y>. MODS MAY NOT WORK UNTIL NUCLEUS IS UPDATED.`), once per Nucleus version and running game, ever (the key goes into `state.json`'s `seen`).
- **Configure:** the shown name, `VERSION`, `NUCLEUS` (the `dependsOn` version for Nucleus, `-` when none), `GAME BUILD` and `RUNS ON: <name> - <meaning>` (story 12); then one line per status problem (as in the tooltips); then the mod's settings from `core.settings.describe` (at most 64), one row each: the label (its `help` as tooltip), the control, and a restart mark for `restart` settings (`APPLIES AFTER A RESTART`, lit while a change waits). `bool` is a checkbox, `enum` a choice, `int`/`number` with `min` and `max` (at most 10,000 steps) a slider with its number box (Default sets the declared default); anything else, and every read-only setting, is a text: the value, or `SET BY <SOURCE>`. A `lobby` setting's control is disabled (`CAN ONLY BE CHANGED IN A LOBBY`). A change goes to `core.settings.setFor`; a refusal puts the control back and shows `NOT SAVED (<code>)`. A mod with none shows `NO SETTINGS`. Text from `mod.json` is shown with control characters as spaces, cut at 64 bytes (help 256).
- `mod.json` is read with a strict bounded JSON reader (`Scripts/json.lua`: at most 65,536 bytes, depth 16, 4,096 values, 1,024-byte strings; never `load` on data). A broken `mod.json` gives one `WARN` per folder per session and a row of `-`.
- **Layout:** core's `screen` host, whose content sits on a card that hugs it (Nucleus 0.12.0). The title, a one-row header list and the list of rows stack in the card's top-left corner; core's BACK is in the bottom-left corner and QUIT GAME, RESTART NOW, the banner and the message line (bottom to top) in the bottom-right. The lists are the layout width less 720 units wide; the list is the layout height less the Mod Manager's 540-unit reserve (540 at layout height 1080, about 10 rows; more scroll), so the card never needs clamping. Configure stacks its lines, its problem lines, its settings list (the layout height less 586, less 46 per problem line) and its message line in its card's top-left corner. The game scales UI by the shortest side (1080 = 1.0), so 1280x720 and 1920x1080 look the same, and a wider screen only widens the columns.
- **Strings:** every string the player sees is in `Scripts/strings.lua`, per language (English required, upper case), picked by the game's language (`GetCurrentLanguage`): the exact tag, then the prefix before `-`, then English.

## What it writes, and when

Only these files, each at the moment a player's click asks for it, and nothing else: no pak, no other mod's files, no shell.

- **`ue4ss/Mods/mods.txt`**, on a toggle click: on sets every line of that folder to ` 1`, and with no line inserts `<Folder> : 1` above the first `Keybinds` line (else at the end), in the file's newline style; off sets every line to ` 0` and inserts none. Only the value after a line's last `:` changes; the BOM, every other byte, the line endings and the trailing newline stay. At most 262,144 bytes. Lines follow UE4SS's matching rule (above).
- **`Mods/<Folder>/enabled.txt`**, on a toggle off: renamed to `enabled.txt.disabled` (a stale `enabled.txt.disabled` is removed first), because UE4SS starts a folder with `enabled.txt` whatever `mods.txt` says. Turning on never touches it.
- **`Mods/ModManager/state.json`**, after a toggle or an alert: `{"version":1,"off":[<folders the player turned off here>],"seen":[<alert keys>]}`, at most 16,384 bytes, 200 `off` and 32 `seen` (the oldest dropped). Read once per session; a corrupt one counts as empty (one WARN) and is rewritten on the next save. The installer will honour it (story 7).
- Settings only through `core.settings` (core writes `Mods/<Folder>/settings.json`), never directly.
- **Atomic writes** (`mods.txt`, `state.json`): `<X>.mm-tmp` written, flushed, closed, read back and compared; `<X>` renamed to `<X>.mm-bak`; the tmp renamed to `<X>`; the `.mm-bak` removed. Any failure puts the previous file back and writes nothing else (an `enabled.txt` rename that fails puts `mods.txt` back too): the checkbox goes back, one WARN, and the window shows `COULD NOT SAVE THE CHANGE`. At start, a missing `<X>` with its `<X>.mm-bak` present (a write cut short between its renames) is restored. Paths are absolute, built only from the game adapter's `Mods` folder and validated folder names.
- **Turning off a mod others need** (another managed row that is on lists its id in `dependsOn`): a confirm window asks first, `TURN OFF <name>? <names> NEED IT.` (at most 5 names, then `AND <n> MORE`) with one `TURN OFF` button; BACK, Escape or any other close puts the checkbox back and writes nothing. Nothing is ever turned off without a click, and nothing cascades.
- Every change applies at the next start: UE4SS reads `mods.txt` and `enabled.txt` only when it starts.
- **Paks are never switched from the game:** renaming a mounted pak crashes the game at its next read (`docs/mod-manager-research.md` 8.2), and nothing runs early enough at the next start to rename it then (8.8). A pak row shows its state in a disabled box until the installer (story 7) or the relaunch helper can apply it (the helper doesn't yet: story 6's open decision).

Log lines (`UE4SS.log`): `[ModManager] CONNECT ok ...`, `READY entry=manage need=>=0.21.0`, `RESTORED <file> from <file>.mm-bak`, `OPEN rows=<n> total=<n> lang=<tag> game=<version or -> build=<build or -> us=<scan and build>` at each open, `MOD <n> <folder> | <name> | <version> | <state> | settings=<yes|no> | need=<..> | build=<..>` once per mod (again when it changes), `STATUS <Folder|pak:key> <none|build,dep,restart> | <tooltip lines joined with " / ">` once per change, `TOGGLE <Folder> on|off`, `CONFIRM <Folder> needed by <n>` / `CONFIRM <Folder> cancelled (<reason>)`, `ALERT nucleus-build`, `CONFIGURE <n> <folder>`, `SET <Folder> <key>=<value>`, `QUIT pending=<n>`, `RESTARTMODE <mode|none (<why>)>`, `RESTART mode=<m> pending=<n>`, and one `WARN` per problem per session.

## How it works

- `Scripts/main.lua`: the dependent bootstrap from core's `api-contract.md`, then `connect{ mod = "ModManager", need = ">=0.21.0" }`. In `onReady` it restores a write cut short, takes the session baseline (the first scan), reads `state.json`, and adds the menu entry (`core.ui.menu.entry`, style `options`). A click reads the running game, scans and opens (or refreshes) the window; a toggle, TURN OFF, a setting and QUIT GAME are its callbacks. Every callback runs under `pcall`, and a fault is logged once with context.
- `Scripts/inventory.lua`: the scan, a pure function over a file system it is given (`listDir`, `readFile`, `exists`), so the unit tests run it offline; the game adapter lists folders and paks through `IterateGameDirectories()`, reads with `io.open(path, "rb")`, and offers `writeFile`, `rename` and `remove` for `files.lua`. No shell, no path built from a name that hasn't passed the name rule.
- `Scripts/modstxt.lua` (the byte-keeping line model), `files.lua` (the atomic write and the `.mm-bak` restore), `state.lua` (`state.json`), `status.lua` (baseline, pending, the build compare, dependency problems, dependents, the alert key): pure, tested offline.
- Mod ids go through core's normalizer `nucleus.modid` and versions through `nucleus.semver` (Nucleus 0.12.0), loaded with `require` like any pure core module. The Configure `NUCLEUS` line follows the shared normalizer only; the dependency check also reads a bare `nucleus` as core's legacy id.
- `Scripts/screen.lua`: the windows. Elements are made once per session and reused at every open (index-based ids `r<n>.on|tg|name|ver|s1..s3|cfg`, settings `s<n>.lbl|cb|ch|sl|ro|rs`); rows past the current count are hidden, never removed.
- If core is missing, disabled, failed or older than 0.21.0, the log has exactly one `[ModManager]` line naming the cause and the mod does nothing else.

## Tests

### Unit tests (no game)

```powershell
./test.ps1                      # or: ./check.ps1 -Scenario unit
```

Lua (any Lua 5.3/5.4 on PATH; MiKTeX's `texlua.exe` is one): `json_test` (the reader, its caps and refusals), `strings_test` (the tables, the picker, `fmt`), `inventory_test` (story 3's I/O matrix against a fake file system, `mods.txt` the way UE4SS reads it, ids and dependencies, the adapter and its write primitives), `modstxt_test` (flips that keep every other byte, CRLF/LF/BOM, the Keybinds insertion, the cap), `files_test` (the atomic write and every failure, the restore), `state_test` (the shape, the caps, corrupt and missing files), `status_test` (baseline, pending, build, dependencies, dependents, the alert key), `screen_test` (the windows against a fake `core.ui`: ids, icons, toggles, status icons, the confirm and alert windows, Configure's controls), `main_test` (the bootstrap, the entry, story 6's I/O matrix end to end over an in-memory file system, writes only to the allowed paths), `driver_test` (the driver loads in every scenario). PowerShell: `deploy_test` (version needs, core ids, `mods.txt` editing, `deploy.ps1` against a fake instance, the fixtures, `build.ps1`'s package), `check_test` (each scenario's checks against synthetic logs), `run_guard_test` (the workspace's run guard).

### Scenarios (in game, unattended)

```powershell
$copy = 'C:\...\nuclear-nightmare\game-instances\v8.2.3-build26601774'
./run.ps1 -Instance $copy -Scenario screen              # in the VM (the default -Target vm)
./run.ps1 -Instance $copy -Scenario screen -Target host # on the host
./run.ps1 -Instance $copy -Scenario restart             # story 8, VM only: RESTART NOW relaunches the game
./check.ps1 -Log <workspace>\dumps\v8.2.3-build26601774\mod-manager\screen.vm.log -Scenario screen -Target vm
```

`run.ps1` deploys with the driver and the fixtures, launches, serves the driver's requests (Enter at the press-any-key screen, real clicks, the wheel, typed text, screenshots in the VM), waits for the end (screen: the game closing itself after the driver's `END result=PASS` and QUIT GAME, or `END result=FAIL`, a crash or the time limit; the others: the driver's `END` line), closes the game, appends `[run.ps1] RUN <how it ended>` and `[run.ps1] FILES unchanged` (or what changed: `mods.txt`'s SHA-256 and the file names under `Content/Paks` and `LogicMods`, after the deploy and after the game closed) to the kept log `dumps/<copy>/mod-manager/<scenario>[.vm].log`, and runs `check.ps1` on it. In the VM it uses the workspace's `tools/vm/vm-sp.ps1` (`-BasePaks` for the fixture paks, `-FileState` for the file check) and Nucleus from `mods/Nucleus/build/package`; take `dumps\vm.lock` around it.

## Layout

| Path | What |
|---|---|
| `mod.json` | The manifest (id, name, displayName, version, scope, game build, UE4SS, `dependsOn`) |
| `Scripts/*.lua` | The mod (what ships): `main`, `inventory`, `json`, `strings`, `screen`, `status`, `modstxt`, `files`, `state` |
| `deploy.ps1`, `deploy-lib.ps1` | Install/remove; the lib holds the version-need check, the core id rule and `mods.txt` editing |
| `build.ps1` | The release package (`-Fixtures`: the fixture pak) |
| `check.ps1`, `run.ps1`, `test.ps1` | Judge a log, run a scenario, run the unit tests |
| `test/ModManagerDriver/`, `test/ModManager{Fixture,Long,Base,Dep,Restart}/` | The driver and the fixtures (never shipped; `ModManagerRestart` only for the restart scenario) |
| `test/unit/` | Unit tests (`fakeui.lua`: a fake `core.ui` and `core.settings`; `memfs.lua`: an in-memory file system) |
